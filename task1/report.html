Task 1 — Web App QA & Debug Report

App under test: RealWorld “Conduit”, the public live demo at https://demo.realworld.show (Angular frontend, source: realworld-apps/angular-realworld-example-app) backed by the public API https://api.realworld.show/api.
Tester: Naman Malhotra  ·  Date: 10 Nov 2026  ·  Browser: Chrome 156 (desktop 1280×800, phone 375×740)
Method: manual walkthrough of every core flow → automated Playwright run of 38 checks (task1/qa-tests/qa.mjs, evidence in results.json + screenshots/) → each frontend finding confirmed by reading the Angular source.

Summary for stakeholders. The happy paths work: you can sign up, log in, write, edit and delete an article and log out. The app “feels broken” because almost nothing has been built for when things go wrong:
  • When the server is slow or has a hiccup, the app just hangs. The home page says “Loading articles…” forever. Deleting can fail silently, and a broken link shows a blank white page. Users get no explanation and no retry button.
  • Forms accept bad input and then show confusing messages. They take a 1-character password and a username made of spaces. A too-long title gives “body title is a string of less than 100 chars”. A large post says “check your internet connection” when the internet is fine.
  • Destructive actions aren't protected. One click deletes an article with no “are you sure?”. A double-click sends the request twice.
  • Account security and accessibility need work before production. The session token is never revoked on logout. Email and password can be changed without the current password. Form fields have no labels for screen readers.
None of these are hard to fix. Most come from one pattern, data requests with no error handling, so a single shared fix addresses several rows at once (see the root-cause analysis).

Root-cause analysis — #1: feed stuck on “Loading articles…” forever

What happens. Whenever the articles API is slow, down or returns an error, the home page keeps showing “Loading articles…” (and “Loading tags…”) forever. The user sees no error, no retry option and no timeout. To them the site simply looks frozen, which is exactly the “it feels broken” complaint.

Why. In src/app/features/article/components/article-list.component.ts, runQuery() sets loading = LOADING and then subscribes to articlesService.query() with only a success callback. When the request fails, the global errorInterceptor normalises the error and re-throws it, but nothing catches it in this component. The stream dies, loading never leaves LOADING, and the template has no branch for a failure because LoadingState has no ERROR value. The tag sidebar uses the same pattern (tags$ with only a tap), and nothing adds a timeout, so a hung connection also spins forever. It is a classic AI-generated-code gap: the happy path was written and demoed, and the failure path never existed.

// today
this.articlesService.query(this.query).subscribe(data => { this.loading.set(LOADED); … });

// fix
this.articlesService.query(this.query).pipe(
  timeout(10_000),
  retry({ count: 2, delay: (_, n) => timer(500 * 2 ** n) }),   // GETs are safe to retry
  takeUntilDestroyed(this.destroyRef),
).subscribe({
  next: data => { this.loading.set(LoadingState.LOADED); … },
  error: () => this.loading.set(LoadingState.ERROR),            // template shows "Couldn't load articles · Retry"
});

How I'd fix it. Add an ERROR state with a “Couldn't load articles · Retry” message, a 10-second timeout, and two automatic retries with backoff (GET requests are safe to retry). Apply the same to tags$. Then add an e2e test that forces a 503 with page.route(), as check F1 does, so this can't regress. Longer term, a shared “remote data” helper (loading / empty / error / retry) for every list and page would also close #2, #6 and #15. Those bugs share the same root cause: error paths were never designed or tested.

Testing notes & limitations

  • Why the live demo. The assessment's suggested demo.realworld.io returns 404 and the old API returns 530. The project moved to realworld-apps, and demo.realworld.show is its official replacement. Testing a live deployment also lets the bonus uptime monitor watch a real public URL.
  • Session isolation. The demo backend deliberately isolates each client's data (“connected to a demo backend that enforces session isolation”). Two observations depend on that sandbox, so I logged them as INFO rather than bugs: (a) signing up with an already-used email is accepted, and the original password stops working; (b) after 12 rapid wrong passwords, even the correct one is rejected with the same “credentials invalid” message (never a 429). Both should be re-tested on a private backend. If they reproduce there, (a) is Critical (account takeover) and (b) is a silent lockout.
  • What passed. Stored-XSS payloads in the title, description and markdown body were rendered harmless by Angular's sanitiser. Protected routes redirect to /login after logout. The API blocks editing another user's article. Wrong-password errors are clear. API latency was about 160–235 ms. A throttled 400 kbit/s, 400 ms network still rendered the feed in about 6.6 s.
  • Etiquette. All test data used throwaway qa_*@example.com accounts on the public sandbox, which is meant for exactly this. Created articles were deleted at the end of the run, and the run sent only a handful of requests.
